# 系统架构

依据已确认的三端分工，本文定义 EAR Desktop 的实现方向。现有云端能力与尚待联调的部分见[云端接口与 MCP](integration.md)。

| 位置 | 职责 |
|---|---|
| 手机端 EarRecorder | 录制并分段保存音频，通过 HTTPS 上传云端接收服务。上传失败时保留本地文件并重试。 |
| 云端 EAR | 接收和保存音频及已有的配套 Context，运行识别、入库、归属与分析。对外通过 EAR API 提供经授权的处理结果。 |
| EAR Desktop | 管理云端连接，展示逐句转写、分析结果和已知的处理状态。提供本地 `ear-mcp` 的配置入口。 |
| 本地 AI 客户端 | Codex 或 Claude Code 启动独立的 `ear-mcp` 进程。该进程向已配置的云端 EAR API 查询证据。 |

## 数据流

```text
EarRecorder → 云端接收 → 识别 → 适配器入库 → 分析 → EAR API
                                                      ↑    ↑
                                      EAR Desktop ────┘    └──── ear-mcp ← AI 客户端
```

首版中，“实时分析”指云端在收到**已封口并成功上传的分段**后启动异步处理。它依赖云端部署接通处理触发、识别和分析任务。桌面首版用查询刷新结果；录音中的增量转写或服务端推送需要独立约定。接收成功、转写入库和总结生成是不同阶段。

## 桌面进程

- **Electron 主进程**持有远端 API 客户端、连接配置和令牌。实现连接功能时，API 请求由主进程发起，使用有限超时并按当前连接归属处理响应。
- **React 渲染进程**展示连接、转写和总结。保持上下文隔离及沙箱，通过 preload 暴露诸如“检查连接”“列出记录”的有限能力。IPC 参数和调用来源由主进程验证，渲染进程不持有令牌。
- **本地 MCP 程序**由 AI 客户端按需启动，通过标准输入和输出通信。桌面界面直接读 EAR API，用户可独立查看结果。MCP 与桌面 App 分别建立到同一云端实例的授权连接。

## 数据边界

云端保存原始录音、转写、分析结果及证据引用。桌面保存连接配置和显示偏好，第一版仅在内存中保留已读取的用户内容。切换连接时清理当前结果及分页状态，防止两个实例的数据混在同一窗口。

EAR 当前的普通用户令牌主要绑定身份和数据类型权限。面向不同用户的私有试点时，使用各自隔离的云端 EAR 实例或经验证的数据隔离部署。桌面配置和上传表单的用户字段都无法提供这一隔离。

## 技术选型

Electron 管理 macOS / Windows 应用生命周期和系统集成。React + TypeScript 实现共享界面，Vite 构建渲染进程。桌面端无需安装云端数据库、识别模型或 Docker。发行时，使用同一源码分别构建 macOS Apple Silicon 和 Windows x64 安装包。实际交付的 MCP 可执行文件也需要按系统和 CPU 架构构建及签名。
