# 云端接口与 MCP

上游接口以 [EAR API](https://github.com/Echo-As-Record/Echo-As-Record/blob/dev/services/api/README.md) 和 [接收服务](https://github.com/Echo-As-Record/Echo-As-Record/blob/dev/services/ingest/README.md) 为准。本文记录桌面端怎样使用这些接口，以及还需要云端确认的契约。当前工程骨架尚未发起真实 API 请求。

## EAR API

| 能力 | 状态与使用方式 |
|---|---|
| 检查授权 | 已有 `GET /v1/me`。校验当前 API 地址和普通用户令牌是否匹配。 |
| 读取逐句转写 | 已有 `GET /v1/records/transcript_segment`。按 UTC 时间窗口分页，游标按不透明值处理。 |
| 读取活动和分析结果 | 已有 `GET /v1/timeline` 与通用记录接口。候选读法是 `GET /v1/records/artifact`，通过实际部署确认用于桌面展示的产物类型、筛选条件及证据链接，再完成结果视图。 |
| 查看单条证据 | 已有 `GET /v1/records/{type}/{id}`，可选版本号。访问仍受云端权限约束。 |
| 查看每段录音的处理中、失败和完成状态 | 待约定云端可查询的任务状态接口，以及手机会话、上传分段、入库记录和分析产物之间的关联。仅凭查询不到转写，无法区分尚未生成、失败和没有权限。 |

连接首版使用已部署的 HTTPS API 根地址和普通用户 Bearer 令牌。客户端跟随分页时保留原查询条件。前台按需刷新，只有拿到明确的进行中状态才定期查询，离开页面或切换连接时取消请求。授权失效、网络失败和有效的空结果应分别显示。未取得任务接口时，先实现已入库结果的查询。

计划使用 Electron 的系统支持加密存储保存令牌。云端连接信息与令牌保留在主进程侧，渲染进程通过有限的 IPC 调用读取结果。访问令牌和转写正文不进入日志、示例配置或仓库。生产连接应验证 TLS，遇到跨来源重定向时拒绝继续发送认证信息。

## 上传与分析触发

手机直接调用云端接收服务的 `POST /api/v1/record`，按 EarRecorder 现有协议上传音频及配套 Context。手机上传地址和口令属于接收服务，桌面使用的是 EAR API 地址和用户令牌。

当前接收服务配置事件通知后可启动兼容识别交接。云端需要把转写入库、分析触发、结果持久化和状态接口接好，才能做到每个已上传分段自动分析并在桌面显示。现有分析模块和配置不代表这条自动链路已部署。推进时先确定幂等分段标识、任务状态与重试行为，再用一段带 Context 的合成录音跑通完整链路。

## 本地 MCP

使用上游现有的 `stdio` 入口。开发联调可在 EAR 源码仓库根目录使用：

```sh
uv run --frozen --package ear-api ear-mcp
```

这条命令由 AI 客户端配置启动。通过该进程的环境提供 `EAR_API_URL` 和 `EAR_API_TOKEN`。工作目录应指向上游 EAR 源码，或由启动命令明确选择上游项目。令牌由调用方安全注入，示例只写变量名称。安装版应明确处理 AI 客户端独立启动 MCP 时如何取得凭据，避免假设它能解密桌面 App 保存的凭据。

MCP 首版验收以实际查询 `find_evidence` 为准，验证其返回同一云端实例的已入库证据。个别工具的权限和作用由上游定义。凭据缺失或无权访问应显式报错，工具能被枚举不代表数据查询已连通。
